# Mobile critique — 2026-10-01 (393×852 CSS px @2x)

Scope: 8 screenshot passes (dashboard, messages, viewer, assistant, rules, settings, more, log), 4 zoom

## N1 — minor — Rules (`/rules`, 393×852)

- **Element:** rule 3 match summary (the `.mono`/`<code>` condition line, e.g. `subject contains "Newsletter" OR subject contains "e-In Focus"`).
- **What is wrong:** the condition breaks **mid-word** across lines: line 1 ends `subject con`, line 2 starts `tains "e-In Focus"` — confirmed in a zoom crop (`subject con` / `tains "e-In Focus"`). Cause: `.mono,code{ … word-break:break-all}` (app.py L373–374), which breaks at the line limit regardless of spaces; the rule applies to every mono string app-wide.
- **Source:** `research-lists.md` §/rules — the phone card's L2 match summary "mono, wraps — it is a sentence, not ellipsis fodder"; shared rule 2 (one legible fact per line).
- **Fix:** on `.mono`/`.cond` use `word-break:normal; overflow-wrap:anywhere` so breaks land on spaces except for a single unbreakable token.

## N2 — minor — Viewer (`/messages/<id>`) vs Messages list / Dashboard

- **Element:** the viewer's date line under the H1 (`… · Thu 01 Oct 2026 · 10:30 +0000 · Canvas`).
- **What is wrong:** the same message reads `10-01 18:30` in the Messages list and the Dashboard "Recent mail", but `Thu 01 Oct 2026 · 10:30 +0000` in the viewer — the viewer shows the raw header timezone while lists use the configured display offset (Settings says "Time display offset 8.0 … timestamps show as UTC+8"). Source check: `_display_date()` formats `parsedate_to_datetime(raw)` with `%z` (app.py L3774–3780) while list times go through the display offset (app.py L216).
- **Source:** `research-shell.md` §4 (timestamps must be consistently labeled and interpretable — Cloudscape); the Settings helper text promises UTC+8.
- **Fix:** run the viewer date through the same display-offset formatter; keep the raw header in the existing `title=` attribute (L3646).

## N3 — minor — Messages (`/messages`) — row selection checkbox

- **Element:** the per-row selection checkbox (small empty square, right side of each row).
- **What is wrong:** on phones the checkbox renders 20×20 px (`#bulk .tbl.mcards td.sel input{width:20px;height:20px}`, app.py L589), absolutely positioned with no label expanding the hit area — at/below the 24 CSS px WCAG 2.5.8 floor (the spacing exception would need verification) and far below the 44 px touch floor. Source check; the screenshot only shows it is small.
- **Source:** `mobile-ui.md` §3 (targets ≥44 px on touch; never below 24 px, WCAG 2.5.8).
- **Fix:** `@media(pointer:coarse){ #bulk .tbl.mcards td.sel input{width:24px;height:24px} }` (or pad the cell/label to a ≥44 px target).

## N4 — nit — Rules (`/rules`) — rule action cluster (⤒ ↑ ↓, disable, ⋯)

- **Element:** the move/disable/overflow button group at the bottom of each rule card.
- **What is wrong:** phone CSS pins these at `min-height:40px` (`#rules .tbl.mcards .rowacts .btn{min-height:40px}`, app.py L630) — below the 44 px floor, and the zoom shows a small, tightly packed cluster. The same stylesheet raises plain `.btn` to 44 px for coarse pointers (L767–768), so the ID-scoped rule wins and re-lowers them. (`.tactions` 38 px L661, `.dsx` 38 px L644, `.card .spread + .row` 42 px L651 are the same pattern.)
- **Source:** `mobile-ui.md` §3 (≥44 px); `research-lists.md` §/rules ("`⤒ ↑ ↓` stay as 44 px targets").
- **Fix:** raise L630 (and the sibling rules) to `min-height:44px` under `max-width:767px`.

## N5 — nit — Rules (`/rules`) — page-head action row

- **Element:** "Test against last 200 messages" + "New rule".
- **What is wrong:** both buttons sit in one flex row with `flex:1` each (`#rules … .r-head .row .btn{flex:1}`, app.py L599–601), so on 393 px the 30-character tester label gets ~178 px and must wrap inside the button beside a one-line primary — cramped at best; a text-wrap inside a fixed-height button is also fragile.
- **Source:** `research-lists.md` §/rules — the tester should get "its own full-width action row under the header on phones".
- **Fix:** on phones let the tester form span `flex:1 1 100%` (two stacked rows).

## N6 — nit — Messages (`/messages`) — toolbar zero-state

- **Element:** `Classify all (0)` vs `Learn rules (0)`.
- **What is wrong:** with both counts at 0, `Learn rules (0)` is disabled (grey) while `Classify all (0)` stays fully enabled (black, tappable) and would start a run over nothing. Asymmetric zero-state signalling on two adjacent buttons. Source: the guards differ — `disabled if classify_state.running` vs `disabled if not tagged_count` (app.py L3363–3364).
- **Source:** `research-lists.md` shared rules / §flows ("a disabled control explains the model better than a no-op tap").
- **Fix:** `{{ 'disabled' if classify_state.running or not unclassified else '' }}`.

## N7 — nit — Dashboard vs Messages — classification counter

- **Element:** Dashboard hero meta `3530 classified (99% of 3557)` vs Messages head `3555 messages · page 1 of 36` / `All 3555`.
- **What is wrong:** the two totals for "messages" disagree by 2 across two screens captured minutes apart. May be different populations (moved/deleted mail) — flagged for verification, not asserted as a bug.
- **Source:** `research-lists.md` shared rule 8 (counts carry context); Dashboard "never an isolated number".
- **Fix:** derive both from one counter, or label the denominator ("… of 3557 indexed").
