# Mobile critique — 2026-10-06 (v2)

Viewport: 393×852 @2x phone shots. Yardstick: `docs/ux-benchmarks.md` (Parts 1–2, cited as §n). Everything below was checked against the live template source in `app.py` (line refs included) so claims are code-verified, not eyeballed. Design invariants (square corners, light Vercel theme, Geist, black log panels, blue links) are not flagged as such.

## Verdicts

- **Dashboard — par vs Vercel/Geist dashboard conventions (Part 2 §1, §1 bar).** The heredoc stat is right: "Needs your attention" answers one question and *every* stat is a real drill-down link — `1 need a reply → messages?f=needs_reply`, `0 errors → messages?f=errors`, `0 pending approvals → assistant` (`app.py:2472-2474`) — which is exactly the "hero stat links to the filtered list" bar Gmail's Android home doesn't even attempt. Status chips name state ("Rules live", "LLM on", `app.py:2477-2478`), "Recent mail" rows carry timestamps. Only real ding: a "Settings →" chip squats in the attention card.
- **Messages — par, leaning worse vs Gmail/HEY (Part 1 §1 bar).** Six filter chips with live counts (All / Awaiting LLM / Needs reply / Sorted / Tagged / Snoozed — `app.py:6423-6425`) comfortably clear the "≥2 scoping axes" bar, and the empty state teaches + offers "Check now" (Part 1 §8 bar, `app.py:6332-6337`). But the row has no read/unread affordance (grep: `mark_read` exists only as an *automation action*, never as message state), no thread grouping, no sender bundling — three of the four visible rows are machine senders, and 3,620 messages paginate 100-at-a-time with the only pager at the very bottom.
- **Viewer — par/approaching better vs Gmail+Gemini (Part 1 §3, §5).** Newer/Older nav, one-handed Draft reply / Snooze / Needs reply buttons, inline LLM summary with its *reason* ("why: automated network update, no action needed"), and a correction block labelled "Teaches the models; does not move mail" — that's the §5 "never silently modify mail" contract made visible on the reading surface, which Gmail only matches with a confirm dialog. Draft/reply UI below the fold is collapsed ("Replies · draft and review"), correctly progressive.
- **Assistant — par vs Shortwave (Part 1 §5).** Empty state teaches with six task-shaped prompts (incl. "Find an old invoice"), input + Send sit directly above the tab bar. The gating model is the real story: Ask = queues an approval card, Auto = runs audited (`app.py:3101`), and the dashboard surfaces the pending count — that is §5(c/d) done properly. No tool-action strip is visible in this shot (empty state), so I can't judge the "visible tool actions" clause — uncertainty, not a finding.
- **Rules — better vs Outlook/Gmail rule builders (Part 2 §2 bar).** Ordered rules (index + name + monospace condition + action), per-rule up / down / move-to-top, non-destructive toggles, and *two* dry-run affordances ("Test against last 200 messages", "Simulate a draft") — Gmail's search-first test and Zapier's Test tab, both present on a phone. Missing only Zapier's drag-reorder and its broken-mapping guard; given up/down arrows exist, that's a nit at most.
- **Settings — par vs HIG Settings (Part 2 §5 bar).** Task-named sections (General / AI / Mail / Automation / Search), current values shown and editable (name "Sean", offset UTC+8), per-field helper text, one "Save general" CTA. Holds only infrequent config — no triage actions leaked in — which is exactly the §5 pass condition. Nothing here needs to be in the main flow.
- **More — par vs HIG "More carries the long tail" (Part 2 §5 bar).** Grouped Get started / AUTOMATION / SYSTEM with icons, one-line descriptions, and chevrons; Log, Plugins, Accounts correctly live here, not in the tab bar. One truncated description (Plugins) is the only visible defect.
- **Log — par+ vs Vercel runtime logs (Part 2 §3 bar).** Newest-first, "times in UTC+8" stated, monospace, level chips with counts (All / Errors / Warnings / Info), time windows (15m / 1h / 24h), search + Find, debug toggle, Refresh, and a Pause control with the WCAG 2.2.2 pause mechanism implemented (10 s auto-refresh, `app.py:10272-10301`). Severity colors are text+color (`.logpanel .badge`, `app.py:576-579`) and pass contrast on black. Fails only on mobile arrangement: 10+ controls stacked into one 393 px horizontal scroller, with the *Errors* chip — the single most important filter — off-screen.

## Top gaps vs the commercial bar

1. **No read/unread state anywhere in the message model** — List §1 bar ("unmistakable unread affordance"; Gmail/Apple bold + dot). Grep confirms `mark_read` is only a rule/flow *action* (`app.py:364, 5790`), never a property of a message, so nothing in the list says "untouched by you". A triage app whose whole promise is "what still needs me" shows machine classification instead of human-new. *Fix:* dot + weight on unseen rows, a `New`/`Unread` chip beside the existing six, mark-read on open.
2. **Zero swipe actions on list rows** — Triage §2 bar (Gmail's per-direction swipe incl. snooze + None; Spark's one-swipe read/pin/archive; Fastmail `y`/`d`). Grep for `swipe|touchstart` returns nothing; the only per-row path is tap → viewer → 3 buttons, or checkbox → bulk bar. On a phone-first tool that's the single biggest speed gap vs the bar. *Fix:* configurable swipe (archive / needs-reply / snooze / None) on rows, always with the button equivalents (§7 2.5.7 — satisfied trivially today because nothing is swipe-only).
3. **No thread grouping and no sender bundling** — List §1 bar (Gmail groups threads by default; HEY collapses a dominating sender into one row; Shortwave Bundles; Spark demotes read mail to "Seen"). At 3,620 messages with automated senders (3 of 3 visible rows are `no-reply@…`), the inbox re-creates the noise the classics engineered away. *Fix:* group `Re:` chains, collapse repeat senders into a counted row.
4. **Pagination is phone-hostile: pager only at list bottom, default 100 rows** — `app.py:6401` (`per=100`), pager rendered after the table (`app.py:6339-6347`), with `.plast`/`.pp` and "Last" hidden on mobile (`app.py:755-756`). The top of the list advertises "page 1 of 37" with no control attached. Gmail/Spark never make you scroll a hundred cards to turn the page. *Fix:* duplicate Newer/Older above the list (mobile), or reduce mobile page size with a sticky pager.
5. **No manual refresh at the top of the mobile screen** — §6 bar ("visible freshness state + manual refresh"; Gmail pull-to-refresh, Fastmail `u`). The dashboard hero actions ("Check now", "Open messages") are deliberately display:none'd at ≤767 px (`app.py:2428`) and the header status chip is a non-interactive `<span>` (`app.py:1112`). A refresh may still exist deeper inside collapsed dashboard sections, but where freshness is *displayed* — the top bar — it is not *actionable*. *Fix:* make the "Last check" chip a refresh button (the state machine already exists: disabled-while-running, `app.py:2456`).

## Summary

- 8 screens judged against the benchmark's named peers; **Rules is better than the bar** (real dry-run pair), **Dashboard/Viewer/Assistant/Log/Settings/More are par**, **Messages is the weakest screen**.
- The app's trust model is genuinely strong: approval-gated assistant actions, per-filing Undo, "teaches, does not move" corrections — Part 1 §5's contract, visible on-screen.
- The commercial gap is mobile *triage mechanics*: no unread signal, no swipes, no thread/sender collapse, bottom-only pager — the four things Gmail/HEY/Spark/Shortwave spent a decade on.
- Nothing here violates the design invariants; the failures are product patterns, plus two WCAG-adjacent nits (link contrast on `#fafafa`; nothing else found).
- Next candidate fixes, in order: refresh-in-header chip → unread affordance → row swipe → thread/sender grouping → mobile pager above the fold.
