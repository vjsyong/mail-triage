# Desktop critique — mail-triage, 2026-10-04

Critic pass over 8 desktop screens at 1440×900: dashboard, messages, viewer, assistant, rules, settings, classifiers, accounts.
Yardstick: `docs/ux-benchmarks.md` Parts 1–2, plus `research-lists.md` and `ui-redesign.md`. Square corners, light Vercel-style theme, Geist fonts, black log panels, blue links = deliberate, never flagged. Screens inspected once each + 3 verification zooms. Claims that need a click-through are marked **verify** — the loop driver confirms before fixing.

## Verdicts

- **dashboard** — par vs Linear/Vercel operational dashboards — the Part 2 §1 bar is met: hero stat ("need a reply") links to its filter, every count carries context ("72% of 3607 seen", "queue length"), the status strip names each subsystem's state; soft spots are the unexplained blue config numbers and one % vs count pair to verify.
- **messages** — worse vs Gmail/Superhuman/Spark — the Part 1 §1 bar's core is absent: no unread/read affordance detectable on any of 7 visible rows (verify globally), no sender/category bundling; compensating strength: STATUS + LLM-confidence columns make triage state more legible than any commercial list.
- **viewer** — worse on action placement / better on transparency vs Gmail–Fastmail reading pane — the 2-event audit trail (oldest first) beats Gmail's "moved to Canvas"; but §3 requires the pane to carry its own actions and the "Actions" cluster sits below the 900px fold, with only ← Newer / Older → above it (verify stickiness and where reply lives).
- **assistant** — par chrome / unverified core vs Gmail Gemini + Shortwave — context-aware drawer, history rail, and "every step streams live" copy are good; §5's (b) visible tool actions and (c) confirm+undo for mutations are not evidenced anywhere in the 8 shots (verify with a real conversation).
- **rules** — worse vs Outlook Rules Wizard / Zapier — precedence is strong and deliberately button-only (the brief endorses buttons over drag for WCAG 2.5.7, so no drag is *not* a gap); but §2's dry-run→commit bar is unmet (one global fixed-sample test, no visible results or commit step) and the editable condition→action builder isn't demonstrable from the list (verify).
- **settings** — par vs HIG Settings (Part 2 §5) — six task-named groups, per-card scoped saves ("Save LLM endpoint"), current values and helper text visible on every control; only save-announcement behaviour is unverifiable from a static shot (verify flash/toast).
- **classifiers** — par on auditability / worse on health-vs-next-action vs Zapier run history — "matches on" logic with sample counts (n=95) is the most auditable surface in the app; but "WEAK" states no consequence and no next action, and no dry-run exists.
- **accounts** — par vs the Shopify/Stripe connection-card pattern (per the brief) — status-driven primary action (Re-authorise), badges, token expiry all good; §6 sync bar unmet: no per-account last-successful-sync, no manual sync, and proxy-alive is not server-reachable.

## Top gaps vs the commercial bar

1. **Read/unread is invisible in the list** — Gmail, Superhuman, and Spark all make unread the primary scan anchor (§1 bar: "unmistakable unread affordance"). Seven visible rows share identical weight and colour, no dot, no tint — including today's 10:48 arrival (verify no unread treatment exists at all). For a triage surface built on "what needs me", this is fix #1.
2. **The list is one flat chronological stream — no bundling or split scoping** — HEY collapses a dominating sender to one row; Gmail has categories; Spark's Smart Inbox sorts Personal/Notifications/Newsletters; Shortwave bundles senders. This list's seven tabs are all workflow state (All / Awaiting LLM / Needs reply / Sorted / Tagged / Snoozed / Errors) — "≥2 scoping axes" is met formally, but neither axis is sender or category, so recurring senders (Canvas, HKUST alerts — both repeating in dashboard "Recent filings") flood 1:1 and "high-volume senders collapse" is unmet.
3. **Assistant mutations have no visible trust layer** — Gemini gates every agentic action with explicit confirm + 60s undo; Shortwave shows recommended actions with the user in control at each step (§5 bar (c)/(d)). The copy promises "proposes rules you approve with one click" and "every step shows as it happens" — but no shot shows a tool action, an approval, or an undo/audit surface (verify). For an app that files mail, this is the trust gap.
4. **Dry-run is not first-class** — Gmail previews filter matches before committing and can apply to existing mail; Outlook runs rules on demand; Zapier gives per-step Test + run history + replay (§2 bar). Here: one global "Test against last 200 messages" with no scope selector and no visible results card or commit step (verify post-click), and classifiers have no dry-run at all. Automation you can't rehearse won't be trusted or tuned.
5. **The reading pane doesn't carry its actions** — Gmail/Fastmail/Superhuman keep reply, reply-all, forward, and archive-and-next on the message so triage never bounces to the list (§3 bar; Fastmail `[`/`]`). At 1440×900 the viewer's only above-fold controls are ← Newer / Older → and the "Actions" heading is clipped at the fold (verify). A viewer you can't action from is a dead end.

## Nits

1. **messages** — rows: no unread affordance on any visible row (major; verify it isn't merely "all read") — source: ux-benchmarks Part 1 §1 (THE BAR) — fix: unread = bold sender/subject + dot; read recedes.
2. **viewer** — action area: "Actions" clipped by the fold; no reply/reply-all/forward reachable above it (major; verify layout intent) — source: Part 1 §3 bar — fix: keep the triage action cluster in the header or a sticky bar (reply / archive-and-next).
3. **messages** — pager: "page 1 of 37" shown, but no Older/Newer/per-page control visible in the viewport (major; verify controls exist) — source: research-lists.md §8 + ui-redesign pagination decision ("page X of Y" + Older/Newer) — fix: render the pager so it's reachable without a full-list scroll.
4. **rules** — tester: fixed "last 200", no scope selector, no visible results card or "apply to existing" commit (major; verify post-click) — source: Part 2 §2 bar (Gmail preview→apply; Zapier Test) — fix: scopeable sample + results card with counts + explicit commit gate.
5. **rules** — IF column: unparenthesized OR chains (rule 7: subject PO/DPO OR body PO/DPO), no ANY/ALL control visible (major; verify the editor covers grouping) — source: Part 2 §2 bar (Gmail one-screen AND/OR editor) — fix: grouped condition rendering + match-mode selector.
6. **accounts** — account card: no "last successful sync" and no Sync now; "PROXY RUNNING" ≠ mail server reachable (major) — source: Part 1 §6 bar (visible freshness + manual refresh) — fix: per-account freshness + sync control; separate proxy-life from server-reachability.
7. **rules** — list foot: rule 11 clipped by the viewport; no "showing 1–10 of 11" context (minor) — source: research-lists.md §8 (counts carry context) — fix: count line + sticky header/pagination.
8. **classifiers** — status: "WEAK" + "−1 REMOVED" state no consequence or next action (minor) — source: Part 2 §1 (status = state + action) + research-lists /classifiers ("are they healthy, what do I do next") — fix: legend meaning + inline next action (review dataset / retrain).
9. **classifiers** — action column: "Dataset…" button appears clipped and Matches-On truncates with no on-page expander (minor; verify table width at 1440) — source: research-lists /classifiers (secondary data belongs in row-details) — fix: fix overflow; full logic behind the dataset view.
10. **assistant** — history rail: X delete with no confirm/undo visible (minor; verify) — source: research-lists.md §4 (confirm irreversible; prefer undo — NN/g via brief) — fix: confirm dialog or undo toast.
11. **dashboard** — metrics card: config counts (13/1/2) in blue vs outcome counts in black, meaning unstated (minor) — source: ui-redesign fourth pass ("colour = status only; neutral grey elsewhere") — fix: one neutral treatment or an explicit "active configuration" label pair.
12. **dashboard** — metric pair: "3590 LLM classified · 100% of 3607 seen" — 3590/3607 is 99.5%, so number or % is wrong (minor; verify) — source: Part 2 §1 (counts carry context, never wrong context) — fix: derive the context string from the same source as the number.

---

**Summary.** The machine room is strong — status, audit trails, and counts-with-context beat most commercial email apps. The triage *surfaces* are where the bar bites: unread treatment, a sender/category axis, and on-message actions. The assistant is the differentiator, but its trust layer (tool actions, confirm, undo) is invisible in all 8 shots — evidence needed before calling it at-par. Three verify-firsts: unread affordance, viewer action placement, pager + dry-run results visibility. If only three fixes ship: (1) unread affordance, (2) sender bundling axis, (3) viewer actions above the fold. Then dry-run results, account sync freshness, classifier health semantics.
