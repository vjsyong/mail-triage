## Verdicts — one line per screen

- **dashboard — better vs Vercel/Linear status-card bar (B2 §1 [23][26][16]).** Attention stats
  deep-link to the queues they summarize (app.py:2486-2487), the four state chips name state and
  lead somewhere, freshness ("Last check 1m ago") is always on — the one card that answers
  "what needs me". Watch item: the watched number is rising (2 → 7 → 8 → 9 failed messages across
  four daily captures) and nothing on this screen says what those 9 are.
- **messages — worse vs Superhuman / Spark / Gmail (B1 §1).** Composition unchanged from 10-10
  (search card + "More filters" + chip row + full-width "Classify all (5)" before row 1;
  "3681 messages · page 1 of 37" frames an archive, not a queue; 10-10 measured the first row at
  y≈412 of 852 and the layout is the same), but the row itself improved: sender + subject +
  the mail's own snippet + time now reads like the commercial row.
- **viewer — par vs Gmail / Fastmail reading pane (B1 §3).** Newer/Older, Draft reply / Snooze /
  Needs reply, honest state ("SORTED", "MOVED TO CANVAS", "Teaches the models; does not move
  mail"); loses the point on fold order — machine verdict + correction form + "Replies · draft and
  review" all sit above the message (gap 3).
- **assistant — par vs Shortwave / Gemini (B1 §5).** Taught empty state ("Ask about your mail",
  five unambiguous one-tap chips), model and details disclosed ("Model: mimo-v2.6-9b" +
  "assistant details"). Chat substance is unjudgeable from a capture — flagged, not failed; the
  header drops the app's freshness signal (nit 7).
- **rules — better vs Outlook rules / Gmail filters as experienced on a phone (B2 §2 [11][13][15]).**
  Ordered numbered cards, guards ("keep in place"), mono conditions, both dry-runs ("Test against
  last 200 messages", "Simulate a draft"), non-destructive toggles. Residual: the reorder glyphs
  (nit 6).
- **settings — par vs Gmail / Apple settings (B1 §7, B2 §5 [7]).** Five task-named tabs
  (General / AI / Mail / Sorting & filing / Search); every visible control carries a label, a
  description and its current value ("Sean", "8", "Always load"); per-section save.
- **more — par vs HIG More-menu pattern (B2 §5 [7]).** "Get started" checklist plus
  AUTOMATION / SYSTEM groups with descriptions and chevrons; long-tail destinations only, nothing
  duplicated from the tab bar.
- **log — worse on the error path, par on structure, vs Vercel Runtime Logs (B2 §3 [16]).**
  Structure meets the bar (newest-first, mono, severity as color **and** text, scope line "times
  in UTC+8 (debug lines hidden)", level chips, Pause exists at app.py:10277); the error path still
  ships Python internals to the reader (nit 1) and double-reports failures (nit 2) — the two
  things a reader opens a log for.

## Top gaps vs the commercial bar

1. **The messages fold is still control chrome, not mail.** Search card + "More filters" + chip
   row + full-width "Classify all (5)" all precede the first row; "page 1 of 37" sizes the screen
   as an archive browser. Best: Superhuman and Spark — the list owns the canvas, search and bulk
   actions are one tap away, not permanent chrome (B1 §1). Why it matters: a phone session is
   "scan the top of the queue"; every control above the fold taxes every visit. Fix: search behind
   a one-line trigger, "Classify all" into selection mode (or below the list), target ≥6 rows of
   mail in fold 1.
2. **Failures still don't tell a story, and the failure count is climbing.** 9 failed messages
   today (2 → 7 → 8 → 9 across four captures); the error rows are raw reprs
   (`RuntimeError("abort('command : UID => socket error: EOF')")`, `act failed ({'op': 'move',
   'folder':` …) and each failure logs twice (rule layer + act layer). Best: Zapier's per-run
   history (data in / data out / what failed) [15] and Vercel's structured logs [16]. Why it
   matters: auto-filing is the core promise of this app; a failure needs "what happened + one
   action" on one row, and one number.
3. **The reading pane spends fold 1 on anything but the message.** Subject, action row,
   "Replies · draft and review", "MOVED TO CANVAS", "Correct category"/"Save correction" all sit
   above the body; the message starts mid-screen. Best: Gmail — the message is the message,
   actions compress around it (B1 §3). Why it matters: the viewer is where you *read*; the
   machine's verdict and a rare training form outranking the mail inverts the hierarchy. Fix:
   body first, correction behind a "Fix category" disclosure.
4. **No reply-queue mode.** "Needs reply 10" is still just a filter; the only in-place clear is
   "No reply needed & next" (app.py:6694, conditional on the LLM flag). Nothing runs a HEY-style
   Focus & Reply sequence that clears the queue one message after another (B1 §3 bar). Why it
   matters: the needs-reply set is the app's core work queue; draining it in one continuous mode
   is the highest-leverage loop on a phone. Fix: launch a focus mode from the "Needs reply" chip.
5. **When an LLM summary exists it replaces the message's own snippet.** app.py:6351:
   `{% if m.llm_summary %}…{% elif m.snippet %}…{% endif %}` — the row shows a machine paraphrase
   instead of the mail's words (the fallback added this week only covers the no-summary case).
   Best: Gmail / Spark rows are sender + subject + **the message's snippet** + time (B1 §1 THE
   BAR). Why it matters: the snippet is what lets you decide without opening; an LLM one-liner is
   a second opinion, not a substitute. Fix: snippet always; summary as a secondary badge/tooltip.
