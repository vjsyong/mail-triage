## Top gaps vs the commercial bar

1. **The list still opens as control chrome, not mail.** Search card + chip row + a full-width "Classify all (3)" button consume ≈280–300 CSS px before row 1; 2.5–3 message rows fit above the tab bar. Best: Superhuman / Spark — the list owns the canvas, search is one tap away (B1 §1). Why it matters for triage: a phone session is scan-the-top-of-queue; every control above the fold taxes every visit. Fix: collapse search to a one-line trigger, move "Classify all" below the list (or behind chip overflow); target ≥5–6 rows visible.
2. **The inbox is framed as a paginated archive, not a flow.** "3665 messages · page 1 of 37". Best: Gmail's endless thread flow, Spark's "new on top, read recede", Superhuman's per-Split cache (B1 §1). Why: page boundaries interrupt the drain, and "37 pages" frames the mailbox as backlog rather than a queue to finish. Fix: continuous scroll / "Load more"; keep page framing only for search results.
3. **Failures still don't tell a story — and today it's louder.** Dashboard went 2 → 7 errors in a day; the log shows the same Canvas socket failure as two ERROR rows (rule layer, engine.py:1761 + act layer, engine.py:3162), one of them a raw Python repr; nothing on the error path offers retry/inspect from what's captured. Best: Zapier run history (per-run in/out + explanation, B2 §2 [15]) and Vercel structured logs [16]. Why: auto-filing is the core promise; a failure needs "what happened + one action" in one place. Fix: one operator-language line per failure, a Retry / Inspect action on the row, linked from the dashboard stat.
4. **The log's one-tap path to failures is hidden.** Level chips start at "All" and clip at "Er…" — the actionable Errors view is the one off-screen behind a masked scroll. Best: Vercel's sidebar level filter (Warning / Error / Fatal, always visible) [16]. Why: runtime errors are the #1 reason to open a log, and the default view is "All" over a long history. Fix: order chips by actionability (All, Errors, …) or wrap to two rows.
5. **No reply-queue mode is visible.** "Needs reply 5" is a filter; nothing in today's two captures runs a HEY-style "Focus & Reply" sequence that clears replies one after another in place (B1 §3 bar; HEY reply mode). Hedge: the collapsed "Replies · draft and review" section could hide part of this — unverified, flagged not failed. Why: the needs-reply set is the app's core work queue; draining it in one continuous mode is the highest-leverage loop. Fix: a focus mode launched from the "Needs reply" chip.
