## Top gaps vs the commercial bar

1. **The list opens as control chrome, not mail.** Best: Superhuman / Spark — the list owns the canvas, search is one tap away. Ours stacks a labeled search card + "More filters" + chip row + "Classify all (2)" (6294-6318) above row 1; the capture fits 3 rows of 3,651. Why it matters for triage: a phone session is scan-the-top-of-queue; every control above the fold taxes every visit. Fix: collapse search to a one-line trigger on mobile, keep the chip row, move "Classify all" below the list or behind chips' overflow; target ≥6 rows visible.
2. **The inbox is a paginated archive, not a flow.** "3651 messages · page 1 of 37" + Newer / Older / Last / per-page chips (6363-6370). No benchmark source states a scroll rule; as opinion: every peer's mobile list flows continuously (Gmail endless threads; Spark "new on top, read recede"; Superhuman caches per Split — B1 §1), while page boundaries interrupt the drain and "37 pages" frames the inbox as backlog. Fix: continuous scroll / "Load more"; keep page framing only for search results.
3. **Failures don't tell a story.** The pieces are split across surfaces: the engine log renders raw reprs ("act failed ({'op': 'move', …}): abort('command: UID => Connection is closed. 13')", engine.py:3162), the dashboard card offers "Retry parked" (app.py:2562), and "2 errors" lands on the Errors filter whose rows are plain, with no retry/inspect affordance (6343-6352). Best: Zapier run history (per-run in/out + explanation, B2 §2 [15]) and Vercel structured logs [16]. Why it matters: auto-filing is the core promise; a failure needs "what happened + one action" in one place. Fix: operator-language failure lines with a Retry / Inspect action on the row, linked from the dashboard stat.
