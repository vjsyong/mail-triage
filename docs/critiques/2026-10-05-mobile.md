# Mobile critique — 2026-10-05

Critic pass over the phone shots (393×852 @2x) in `qa/shots/2026-10-05/mobile/`.
Yardstick: `docs/ux-benchmarks.md` (read in full; cited by section), plus
`docs/messages-mobile.md` and `docs/dashboard-mobile.md` for page intent.
Method: each screenshot inspected once + 4 zoom crops (viewer top, viewer bottom,
list top/row anatomy). No external fetches needed — the benchmark doc is
first-party sourced. Design invariants (square corners, light theme, Geist, black
log panel, blue links) excluded by rule.

## Verdicts

- **Dashboard — better** vs the Vercel/Geist dashboard bar (bench P2 §1, §6):
  hero stat answers one question and links to its filtered list ("0 need a reply ·
  flagged by the LLM" → `view →`), status is text-not-colour ("All systems
  normal"), freshness is explicit ("Last check 2s ago") with a "Check now" manual
  refresh — and **"Recent filings" + one-tap Undo is above the bar**: Gmail only
  offers a transient undo toast; a persistent machine-move ledger with per-row
  Undo is a stronger trust pattern for an auto-filing app (bench P1 §2 undo bar,
  §5d "never silently modify mail — keep undo reachable").
- **Messages — worse** vs Gmail's list (bench P1 §1): 3 of 6 bar items unmet —
  no threads/grouping, read rows don't recede, no sender collapsing — and only
  ~3 rows fit per screen. It does show more triage telemetry per row than Gmail
  (LLM→folder badge + confidence %, NEW badge, bulk checkboxes, status filters
  beyond All), but scanning the queue is the job, and scanning is slow. No search
  control on the surface either (see gap 2).
- **Viewer — worse** vs the Gmail/HEY reading pane (bench P1 §3): the pane carries
  *navigation* (`← Newer` / `Older →`, "View plain text") and zero *decisions* —
  no reply/reply-all/forward, no archive-and-advance, no flag-needs-reply, no
  mark-read at first paint; the audit trail sits below the message body, past a
  full promotional email. Bench: "reading must carry its own actions so triage
  never bounces to the list" — here every decision bounces.
- **Assistant — par** vs the AI-surfacing bar on the one state visible (bench P1
  §5, P2 §8): empty state = title + 4 real scenario chips ("What can you do?",
  "Summarize my inbox", "Suggest rules for me", "Find an old invoice") — more than
  the bar's "one action"; model transparency via an "assistant details" expander.
  Chat-side gating isn't verifiable from a still (prior rounds: X-delete arms in
  place, actions logged).
- **Rules — better** vs the Gmail/Outlook/Zapier rule-builder bar (bench P2 §2):
  two dry-run affordances — "Test against last 200 messages" (run-on-existing,
  à la Outlook) and "Simulate a draft" (à la Zapier's test tab); ordered
  move-to-top/up/down controls, non-destructive per-rule toggles, condition and
  action each on one row in mono.
- **Settings — par** vs the HIG settings bar (bench P2 §5): task-named sections
  (General / AI Settings / Language model / Classifiers), every field shows its
  current value with a one-line purpose ("Your name" → Sean), per-section save.
- **More — par** vs the HIG "More" model (bench P2 §5): long-tail destinations
  grouped AUTOMATION (Rules, Simulator, Flows, Learning, Templates) and SYSTEM
  (Accounts, Log), one-line subtitles, "Get started" checklist as the first-run
  anchor (bench P2 §8).
- **Log — par** vs Vercel's runtime-log bar (bench P2 §3): pauseable auto-follow ✓
  (many mobile logs lack it), severity as text + colour (INFO / WARN / PLUGIN),
  newest-first with the timezone stated, mono timestamps, line filter. Missing
  from the bar: a time-window filter.

## Top gaps vs the commercial bar

1. **The reading pane carries no decisions.** Best: HEY (Focus & Reply — reply
   through a queue, items drop off) and Gmail (inline reply/archive +
   auto-advance). Bench P1 §3: "reading must carry its own actions so triage never
   bounces to the list." For an app whose filters include "Needs reply", the only
   loop on a message is read → back → act. Reply, flag, move, mark-read belong on
   the pane, pinned where the thumb lands.
2. **No search on the Messages surface.** Best: Gmail (search is the list's
   primary affordance) and Fastmail ("any search result can become a rule" —
   bench P2 §2). Retrieval exists (the assistant chip "Find an old invoice"
   implies an index; More's checklist names a search index) but the only surface
   is a chat. 3,610 messages across 37 pages with paging as the only list-level
   retrieval is a triage dead-end; a search box that also seeds a rule is the
   Fastmail lesson.
3. **No inline AI on the open message.** Best: Gmail Gemini (inline
   summarize/draft, mutations gated + undo), Shortwave (assistant works on "any
   email on your screen"). Bench P1 §5(a) asks for exactly this. The assistant is
   a separate destination — from a long newsletter you cannot summarize or draft
   without leaving the message.
4. **No snooze / deferral anywhere.** Best: Gmail (swipe config incl. snooze),
   Spark, Superhuman (Auto Reminders resurface unanswered mail after 1–7 days —
   vendor claim). Bench P1 §2 bar includes snooze presets. A needs-reply queue
   without "not now, not never" forces every decision into now-or-ignore — the
   exact failure triage apps exist to prevent.
5. **No grouping of any kind: threads, splits, or sender bundling.** Best: Gmail
   (threads by default), HEY ("a dominating sender collapses to one row"),
   Shortwave (Bundles), Spark (Seen section). Recurring senders (weekly menus,
   newsletters) arrive as fresh 4-line rows every week and the All view scans
   linearly. Bench P1 §1: grouping cuts rows; bundling stops one sender
   dominating.

## Summary

Dashboard and Rules beat their commercial bars (filing ledger + undo; two
dry-runs); Log, Settings, More and the Assistant empty state hold par.
The two drags: Messages is a scan surface with ~3 rows/screen and no read
recession, search or grouping; the Viewer carries navigation but no decisions —
every triage act bounces back to the list. Biggest gaps vs Gmail/HEY/Shortwave:
reading-pane actions, list search, inline AI, snooze, sender/thread grouping.
Fix order: viewer actions → list search → row density/recession → grouping → snooze.
