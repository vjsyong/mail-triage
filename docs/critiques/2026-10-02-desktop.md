Critic pass over 8 desktop shots: dashboard, messages, viewer, assistant, rules, settings, classifiers, accounts.
Yardstick: `docs/ux-benchmarks.md`, cited as **P1 §n** (Part 1 — email-product benchmarks) and **P2 §n** (Part 2 — cross-app craft/standards). Briefs skimmed: `research-lists.md`, `research-shell.md`. Method: each shot inspected once; 4 verification crops (messages header/rows, messages confirms no search box & no unread affordance; viewer header; viewer cards; dashboard stat tiles). Two claims below that can't be settled from stills are flagged as uncertainty.
Context: self-hosted single-user triage app — rules sort most mail, a local LLM classifies the rest, learning loop on top. Phone-first, but this pass judges the desktop build only.

## Verdicts — one line per screen

- **Dashboard — par vs Vercel's own status/log conventions [16] and the stat-card bar [23][26].** Bar: hero stat answers one question and links to the filtered list it summarizes; a status card names state + next action; "recent" data is timestamped; no dead KPI tiles. We do the hard parts well — four systems each state a condition plus detail (`connected · checked 46s ago · next in <44s`, `ready · 6644 chunks · folders 18/18`, `28/40 calls this hour · fallback deepseek-chat`), freshness lives in the sidebar foot ("Last check 46s ago"), filings are timestamped, each row carries Undo. But 6 of 7 stat tiles dead-end (crop-confirmed: only "need a reply" shows a blue `view →`), and "Recent filings" shows the same filing three times — reads broken even if it isn't.
- **Messages — worse than the Gmail/Superhuman list bar (P1 §1); better than Gmail on row intelligence.** The bar: sender + subject + snippet + time + unmistakable unread affordance; ≥2 scoping axes; read items recede. We do: 7 status filters with live counts (far past "≥2 axes"), bulk select, and per-row STATUS + LLM chips with confidence (`Notification (97%)`) that Gmail rows simply don't carry. We don't: any search box or folder scope (crop-confirmed absent), any unread affordance on any row (crop-confirmed: no dot, bold, or count), consistent row anatomy (snippet on some rows only), and density is ~6 rows per 900px — low for a desktop triage surface. The filters are pipeline states (Awaiting/Sorted/Tagged/…), which is distinctive, but mailbox structure — the folders the automation writes into — is not a scoping axis anywhere.
- **Viewer — worse than the reading-pane bar (P1 §3 / Gmail–HEY–Fastmail); better than every peer on triage provenance.** The bar: next/prev + archive-and-advance + reply/reply-all/forward; AI replies land as editable previews; handling never bounces back to the list. We do: `← Newer / Older →`, `View plain text`, and an **audit trail no commercial client shows** — "How this email was triaged, oldest first · 2 events" naming the rule and the folder — plus a Details card (From/To/Date/Folder/Message-ID). We don't: any reply / reply-all / forward / archive / snooze / move / tag control (header crop: none; the only message action visible is the Actions card's "Classify with LLM"), and reply routes through the assistant's "Suggest a reply". `MOVE:NEWSLETTERS` sits over the body as raw action code. A triage app that can sort but can't act from the reading surface is missing the last mile.
- **Assistant — par vs Shortwave/Gemini framing (P1 §5); transcript rendering unverified.** The bar: chat that can search/act across the mailbox with visible tool steps; mutations confirmed + undone; agentic permissions visible. We do: two surfaces (full page + persistent side panel with per-page context), context-aware starter prompts ("Summarize this email" on the viewer, "Explain my rules", "Is my connection healthy?"), an empty state that teaches (title + reason + 4 entry actions, P1 §8), and a permissions footer — `may do directly: classify, flag, tag, move…; disabled: delete, send` — that exceeds the P1 §5(c) visibility ask. Can't judge conversation/tool-step rendering from an empty-state shot; the history rail shows near-duplicate test threads with bare ✕ deletes.
- **Rules — par to better vs Outlook [13]/Gmail [11], behind Zapier [15] on run history.** P2 §2 bar: ordered conditions/actions, non-destructive toggle, dry-run before commit, guarded reorder. We do: numbered top-to-bottom table with first-match-wins stated in plain words, guard rules ("keep in place") the copy explicitly teaches, pin/↑/↓/disable/edit/delete per row (buttons, not drag — right call per research-lists §5), and two dry-runs ("Test against last 200 messages", "Simulate a draft"). We don't: per-rule match counts or last-fired (Zapier logs every run), and the MATCHES column contains the condition sentence — the label invites a counts read that never comes.
- **Settings — par vs HIG §7 / Gmail General (P1 §7); craft gaps, not structure gaps.** The bar: task-named sections; every setting shows its current value; saves emit status. We do: a task-named sub-nav (AI Settings → Language model / Classification / Classifiers / Embeddings & reranker / Assistant; Mail & connection; Sorting & filing), per-section Save buttons, current values visible (`Sean`, the LLM base URL, model), and an honest scope note ("Blank fields fall back to the env file"). We don't see: a saved/changed-state indicator (unverifiable in a static shot — flag for the DOM pass), or a shortcut reference (P1 §7 / P2 §5 bar); the offset value renders as "8.0".
- **Classifiers — worse than the product's own pitch; better than the field on honesty.** Peers show no classifier scoreboard either (Gmail/Outlook rules show none — P1 §1/§2), so judge against the app's promise plus the stat-bar principles [23][26]: the page sells "faster, consistent, and immune to instructions hidden inside email content" — and shows no accuracy, coverage, last-fired, or corrections-in-window. "WEAK" is a badge without a number. Internals leak (`__other__` classes, `decision_list` kind, a `-1 REMOVED` fragment under SAMPLES). In this shot the only row action is "dataset". What's genuinely good: explaining *why* heuristics run before the LLM, and a visible feedback trail.
- **Accounts — par to better vs the integration-status pattern (Stripe/Shopify via research-lists §accounts) + the freshness bar (P1 §6).** Proxy strip names state with port and uptime (`PROXY RUNNING · 127.0.0.1:1993 · up since 10-02 10:31`) and offers Restart/Proxy log; the account states its credential contract ("access token until 10-02 11:31 · loopback mode") with word-badges (READING, AUTHORISED) and a status-driven primary ("Re-authorise"). Cryptic leftovers: `pld 11` and `loopback mode` without a gloss on the strip itself. Add-account form not in this shot — form quality unjudged here.

## Top gaps vs the commercial bar

1. **The reading pane can't finish the job — no reply / archive / snooze / move / tag controls in the viewer.** Visible controls are `← Newer / Older →`, `View plain text`, the `MOVE:NEWSLETTERS` status label, and an Actions card whose only button is "Classify with LLM"; replying routes through the assistant. Best in class: Gmail (auto-advance defines post-handling flow), Fastmail (`r/a/f`, `[`/`]` archive-and-move-on), HEY (Focus & Reply clears replies in place) — P1 §3, whose bar is explicit: "next/prev + archive-and-advance + reply/reply-all/forward." Why it matters: triage ends in *doing*; today the fastest path from "read" to "done" isn't in the reading surface.
2. **The output of auto-filing is not browsable: no plain search field, no folder scope, no per-folder view.** Filters scope by pipeline state; semantic search exists only inside the assistant chat (a real differentiator, not a substitute for a scannable browse). Best in class: Gmail (search + labels), Superhuman (Split Inboxes + search, P1 §1), Fastmail (any search result can become a rule, [12]). Why it matters: most mail is filed into folders by rules/LLM ("folders 18/18" indexed); if the user can't open *Newsletters* or search by eye, the automation's results are only half-visible.
3. **No keyboard model surfaced anywhere on desktop.** No command palette, no single-key affordances, no shortcut reference in any of the 8 shots. Best in class: Superhuman (`Cmd/Ctrl+K` master command with every action's shortcut beside it) and Fastmail (`j/k/x/d/y/z`, `z` undoes up to the last 10 actions) — P1 §2, whose bar wants ≥5 single-key actions; P1 §7's bar wants a shortcut reference. Why it matters: desktop triage velocity is this product class's whole argument; the app is mousebound.
4. **The learning loop has no scoreboard.** Rules show no match counts or last-fired; classifiers show samples + rule internals but no accuracy/coverage/precision; "WEAK" is a word, not a number; dashboard automation stats are cumulative totals with no per-actor breakdown (rules vs LLM vs flows). Best in class: Zapier's Zap History (every run logged, [15]); the dashboard doctrine says a stat answers one question and leads somewhere [23][26]. Why it matters: the pitch is that rules + a local classifier + learning handle most mail — trust in that loop needs visible hit rates on rules and classifiers.
5. **Undo/confirmation is only surfaced for machine filings.** The only undo affordance in the eight shots is the per-row "Undo" on Recent filings ("Undo puts one back and keeps automation off it" — good). Nothing advertises undo after a *user* triage action, or a global stack. Best in class: Fastmail `z` (undo up to the last 10 actions — P1 §2), Gmail's 30s send undo (P1 §4), and P1 §2 THE BAR's "global undo (toast or ~10-action stack)" + "destructive actions confirmed or undoable". Why it matters: fast single-user triage is mistake-prone; undo is the cheapest confidence there is.

## Nits

Severity: blocker / major / minor / nit.

1. **(minor) Dashboard · "Recent filings"** — the same filing appears three times with identical subject and timestamp (`YONG VI Jun Sean shared…`, 10-02 09:48). If three real filings, rows must disambiguate (count/ref); if duplicates, dedupe. Source: P2 §1 bar — "recent" feeds must be trustworthy; uncertainty: can't tell data vs render from a still.
2. **(minor) Viewer · gray `MOVE:NEWSLETTERS` label above the body** — raw action code as status. Should read "Filed to Newsletters · Undo". Source: P1 §5(d) (keep undo reachable at the mutation); research-lists §7 (no jargon).
3. **(minor) Internal tokens leak into UI across four screens** — `__other__` / `decision_list` / `-1 REMOVED` (classifiers), `Newsletters uid 1627` (viewer Details), `pld 11` (accounts proxy strip), `MOVE:NEWSLETTERS` (viewer, see #2). Human labels everywhere; raw IDs stay inside the black log panels. Source: research-lists §7 (no jargon); P2 §8 craft (meaningful states).
4. **(minor) Messages · row anatomy varies** — some rows are one line with no snippet (rows 1, 5 of the shot), others two lines with snippet; the scan rhythm breaks. Source: research-lists §2 (identical element order row to row); P1 §1 bar (row = sender + subject + snippet + time consistently).
5. **(minor) Messages · no unread affordance on any row** (crop-confirmed: no dot, no bold, no count). P1 §1 THE BAR calls for an "unmistakable unread affordance" and P1 §2 relies on mark read/unread. If read state isn't tracked, say so somewhere visible; if it is, surface it.
6. **(minor) Messages · zero-count toolbar actions** — "Classify all unclassified (0)" and "Learn rules from tags (0)" sit in the toolbar as if actionable. Zero counts should be unmistakably disabled and teach ("nothing to classify yet"). Source: P1 §8 empty-state bar; research-lists §7.
7. **(minor) Assistant · history rail** — near-duplicate test threads ("Help me create a draft to test…" ×3, "How do I use this page?" ×2) and each has a bare ✕ delete with no visible confirm/undo. Clean seed data; give chat deletion an undo toast. Source: P1 §5(c) (mutations confirmed + undo); P2 §8 craft (destructive states).
8. **(nit) Rules · MATCHES column label** — the column holds the condition sentence, not match results. Rename to IF/CONDITION, or fill it with counts (see gap 4). Source: P2 §2 bar; research-lists §8 (counts carry context).
9. **(nit) Dashboard · dead-end stats** — 6 of 7 tiles don't link (crop-confirmed); the matching Messages filters already exist (Sorted/Tagged/…), so each tile can deep-link cheaply. Source: P2 §1 THE BAR [23][26].
10. **(nit) Settings · offset shows "8.0"** — display "8" or "+8". Source: P2 §8 craft (a default the design system wouldn't ship).
11. **(nit) Settings · no saved/changed indication visible** — "Save general" / "Save LLM endpoint" show no saved state or dirty marker in this shot; verify a post-save status message exists and is announced. Source: P2 §5 bar ("saves/sync emit announced status messages") [7][3]; uncertainty: a static shot can't show a toast.

## Summary

- Strong bones: triage provenance (audit trail, per-row status/LLM chips, dashboard status strip with state+detail) is genuinely ahead of Gmail/HEY/Fastmail; rules engineering (guards, order, dry-runs) is at Outlook-par+; the assistant's permissions footer is a model for the category.
- Three structural misses on desktop: the viewer can't act on mail, the filed mailbox can't be browsed (no search field, no folder scope), and there's no keyboard model — table stakes in this product class (P1 §1–§3, P1 §2/§7).
- The learning loop is closed but unmeasured — no match counts, no accuracy, no last-fired anywhere (gap 4); fix alongside the measure-to-trust doctrine [23][26].
- Undo exists only for machine filings; user actions and destructive controls (rules delete, chat ✕) need the P1 §2 global-undo treatment.
- Craft is close: token leaks (`__other__`, `decision_list`, `uid 1627`, `pld 11`), inconsistent list rows, and a duplicate-looking feed entry are the visible rough edges.
- Net: a credible triage *engine*; the desktop *process* around it trails the commercial bar by roughly one generation on acting, browsing, and speed.
