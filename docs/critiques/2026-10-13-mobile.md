## Verdicts — one line per screen

- **dashboard — better vs the Vercel/Linear status-card bar (B2 §1 [23][26][16]).** Bar: hero stat answers one question and links to the filtered list it summarizes; status names state + action; "recent" is timestamped. We deep-link both attention counts, keep freshness on-screen ("Last check 39s ago"), and timestamp every recent row. Below par only in that the red 10 still explains nothing on the surface that shows it, and the 4th tile of a 2×2 status grid is a Settings nav link **(p)**.
- **messages — worse vs Superhuman / Spark / Gmail (B1 §1).** Their bar: row = sender + subject + snippet + time + unmistakable unread affordance; grouping cuts rows; read mail recedes. Ours has a commercial-grade row (sender + subject + snippet + time + status/classification badges, status-recessed) but the screen still opens on furniture — search card, "More filters", chip row, "Classify unclassified (6)" — so row 1 lands around mid-screen and roughly two rows fit a viewport, and "3702 messages · page 1 of 38" frames the surface as an archive rather than a queue. Nothing on the row can be acted on: no gesture handlers touch rows anywhere (10-12 gap 5, still open).
- **viewer — par vs Gmail / Fastmail reading pane (B1 §3).** Bar: next/prev + archive-and-advance + reply/reply-all/forward; the pane carries its own actions. We ship honest state, Newer/Older, Draft reply / Snooze / Needs reply, and the machine's reasoning on-screen ("LLM summary: … · why: … · filed to Newsletters") — better than anyone in B1 at *explaining* a machine decision. Held to par by two things: no archive-and-advance unless the LLM already suggested a folder (`can_file`), and the fold-leading correction form/reply panel **(p)**.
- **assistant — par vs Shortwave / Gemini (B1 §5).** Bar: inline summarize + chat with visible tool actions + every mutation gated by confirm and undo (60s floor). Empty state is above the §8 bar (title + five one-tap chips + input anchored above the tab bar) and the model is disclosed ("Model: mimo-v2.6-9b"). The mutation gate is unobservable in a still — flagged, not failed; the header still drops the app's freshness signal **(p)**.
- **rules — better vs Outlook / Gmail / Zapier rules as experienced on a phone (B2 §2 [11][13][14][15]).** Bar: ordered editable condition→action, non-destructive toggle, a dry-run before commit. We ship ordered numbered cards, mono conditions (`from contains "kevinpereira@ust.hk"`), guard semantics ("keep in place (guard)"), **two** dry-runs above the list ("Test against last 200 messages", "Simulate a draft"), and reorder + overflow per card — more than Outlook's run-on-existing or Gmail's verify-by-search.
- **settings — par vs Gmail / Apple settings (B1 §7, B2 §5 [7]).** Bar: task-named sections, visible labels, every setting shows its current value, ≤2 hops from the surface it changes. Five task-named tabs (`General · AI · Mail · Sorting & filing · Search`), label above input, description below, value visible ("Sean", "8", "Always load") — B2 §4's label rule passed. Held at par by the save row having no dirty/saved state **(p)** and by send-safety settings not surfacing on the captured tab (see gap 4).
- **more — par vs the HIG More-menu pattern (B2 §5 [7]).** Long-tail destinations only (Get started checklist, AUTOMATION, SYSTEM), each with a description and a chevron, nothing duplicated from the tab bar. "Get started" as a persistent checklist is the §8 first-run contract done better than Superhuman's progressive reveal. Only the Plugins description is unfinished **(p)** and there is no version/build line.
- **log — par on structure, worse on content, vs Vercel Runtime Logs (B2 §3 [16]).** Bar: level filter + time window + search + live-tail toggle; newest-first; UTC; severity in colour *and* text; mono IDs; pauseable. Content still fails: the WARN row prints the server's wire text verbatim.

## Top gaps vs the commercial bar

1. **No reply-queue mode — the app's core human queue still has no way to be drained in one motion.** "Needs reply" is a filter chip; the single in-place clear is conditional and lives inside the viewer (`can_file` / `llm_needs_reply`). Best: **HEY Focus & Reply** — shows *only* Reply Later mail and clears items one after another, "knock out 5 of 12, or all 12, or none" (B1 §2, §3). *Why it matters:* this number is the app's promise and it moved 10 → 13 in a day; a queue that grows while offering only push → act → pop is the highest-friction loop on a phone. (p, one day older and larger)
2. **Rows have no actions, so triage is never thumb-level.** No pointer/touch handler touches a list row (10-12 gap 5, re-verified); every item costs open → act → back, and the only per-row control is the 24×24 checkbox feeding the bulk bar. Best: **Gmail / Spark** — per-direction swipe (archive, snooze, mark read, **None**) with a button path kept for WCAG 2.5.7 (B1 §2, B2 §7 [3]). *Why it matters:* a triage app is judged on items-per-minute; the row is where the phone spends its time.
3. **Failure still has a number but no story, and the number is climbing.** Dashboard "10 failed messages" → a filtered list; log "Errors 5" → error log rows; neither shows, per failure, the message + the rule + the reason + Retry/Open. Best: **Zapier's per-run history** (data in / data out / what failed) [15] and Vercel's structured logs [16]; B2 §1 requires a status surface to name state *and* next action. *Why it matters:* auto-filing is this app's core promise, so a filing failure must be as triageable as a message. (p)
4. **No send-safety at all — no undo window anywhere in the product.** Send is the one irreversible action and every peer buys back seconds: Gmail 5/10/20/30s with Undo, Fastmail a 20s **server-side** hold ("a client-side delay means you can think it's been sent when it hasn't"), Apple 10s configurable, Spark 5s default (B1 §4, §7). Our outbound path is the assistant composer (`/assistant/send`, app.py:8352); repo-wide there is no unsend/undo-send string, no delay, no "sent — Undo" moment, and no setting for it. **Best: Fastmail.** *Why it matters:* it is the only action a triage tool performs that cannot be walked back with a filter.
5. **The fold is control chrome, not mail.** Search card + "More filters" + chip row + a full-width bulk button are permanent furniture above row 1, and "page 1 of 38" announces an archive. Best: **Superhuman / Spark** — the list owns the canvas; search and bulk actions are a tap away, not standing chrome (B1 §1). *Why it matters:* a phone session is "scan the top of the queue"; every control above the fold taxes every visit. (p)

## Summary

- Verdicts: 2 better (dashboard, rules), 5 par (viewer, assistant, settings, more, log structure), 1 worse (messages); log content is the worst single defect class in the set.
- Landed since 10-12: "Classify unclassified (6)" noun restored, Errors chip promoted to second position, dashboard unit labels holding.
- New this round: **no send-safety anywhere in the product** (gap 4 — Fastmail's server-side hold is the model), the viewer's triple-rendering of one machine verdict, and a tab bar that carries no badges for the queues it navigates to.
- Unchanged and load-bearing: rows still have no actions, the fold is still chrome, and failure still has a count but no story.
- Trend to watch: need-a-reply 10 → 13 and failed messages 9 → 10 in one day; the two numbers the dashboard watches are the two that got worse.
